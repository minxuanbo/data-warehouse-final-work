## 2 开发顺序

### 第一步 获取并验收数据

从 Olist 发布页面下载完整 CSV，保存到 `data/raw/`。保存来源 URL、下载时间、许可和 SHA-256。逐表输出行数、字段、候选键重复情况、空值数量和日期范围。检查订单与客户、明细与订单、支付与订单、评价与订单的关联覆盖率。

输出 `data/manifest.csv`、`reports/data_profile.md` 和字段字典。不得只复制选题材料中另一台电脑的行数，也不要把客户记录数直接写成独立用户数。不要生成模拟订单作为正式项目数据。

### 第二步 建库与冻结口径

创建开发数据库 `olist_dw` 后，使用 `scripts/warehouse.py init` 安装完整的两份初始化 SQL 及版本记录，或直接用 `run` 自动初始化并执行 ETL。不要仅手工执行第一份 SQL，导致后续 CLI 缺少版本记录。

项目虚拟环境准备好后可使用：

```powershell
.\.venv\Scripts\python.exe scripts/warehouse.py run
```

账号和密码由实际环境配置，不提交到 Git。确认数据字段与设计一致后，冻结订单状态集合、时间比较规则、代表评价选择规则和各事实粒度；若发现源数据不符合契约，更新设计并记录原因。

### 第三步 打通最小链路

先开发订单、客户、商品、卖家及明细的导入和转换。维度先于事实装载，订单先于明细装载。生成月度已送达订单数和商品销售金额，用独立 SQL 与 CSV 对账，再制作一张交易趋势图。

完成标准：从全新数据库可以重复运行；订单主键唯一；一行一单的宽表行数不增加；月度商品金额与同状态、同月份的来源明细一致。只有此链路通过后再扩展。

### 第四步 完成支付 履约 评价

加入支付事实，先按订单汇总再连接；加入代表评价的稳定选择；按有效时间集合计算配送耗时和逾期率。补充 `trade_day_category`、`trade_day_seller` 和 `delivery_review_group` 模型及相应 ADS 视图。地理坐标地图属于可选功能，州和城市分析为必做项。

完成标准：不同事实的金额不重复；同一订单最多一条代表评价；无评价不算零分；预计到货当日送达不算逾期；日指标汇总到月时重新累加分子分母；多卖家或多品类订单不会被误加成全局订单数。

### 第五步 完成三个看板

| 看板 | 建议组件 | 需要同时展示 |
| --- | --- | --- |
| 交易概览 | 已送达订单数、商品金额、客单价、月度趋势、州/品类/卖家排名 | 币种、已送达过滤条件、下单日期范围、边界月份说明 |
| 履约分析 | 平均配送耗时、逾期率、各州对比、耗时分布 | 有效订单数、缺失/异常时间数量；订单级配送口径 |
| 用户评价 | 平均评分、低分率、评分分布、逾期与未逾期评分对比 | 有效评分样本数、两组样本量、相关性解释 |

第一版使用 SQL 或 dbt 维护统一指标，避免每个图表各写一套口径。对比组样本量较小时提示谨慎解释，不写未经数据支持的业务结论。

### 第六步 集成与提交

锁定依赖，验证从 README 可以完成初始化、导入、转换、质量检查和看板启动。保留运行命令、质量结果和关键 SQL。按老师模板补齐第六至八章，填入实际机器配置、版本、ETL 截图、血缘图和真实结果。

录屏覆盖：数据来源与表结构、执行一次 ETL、查看质量检查、三个看板筛选和下钻、选一个指标回查 SQL。答辩前全员彩排，按老师实际时长要求安排内容。最后提交报告、代码、PPT、关键功能录屏；压缩包按各组员姓名用连字符连接命名。截止日期以教师后续通知为准。

## 4 答辩应能回答的问题

1. 为什么订单、商品明细、支付必须分开建事实表？直接连接会产生什么后果？
2. 为什么 `customer_id` 不等于独立购买者？为什么用户数不能跨地区简单相加？
3. 订单量使用哪些状态，金额是否含运费，客单价分子分母是否一致？
4. 预计到货日期只有日期含义时，如何避免将当天到达误判为逾期？
5. 缺失评价和异常时间如何处理，为什么不能补成零？
6. 为什么先全量处理历史快照，按月分批为什么不是真实实时接入？
7. 选用 PostgreSQL 而不是分布式引擎的依据是什么，如何用实际性能验证？
8. 如何证明看板金额没有重复、质量检查有效、项目能够从空环境重建？
