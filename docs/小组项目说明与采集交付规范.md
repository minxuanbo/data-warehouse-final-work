# 四人小组项目说明与采集交付规范

版本：2026-10-30。供组内讨论与任务认领使用；成员暂用 A/B/C/D 表示，姓名、学号和具体截止日期由组内补齐。本说明规定协作和采集接口，不替代前五章设计文档，也不表示数仓已经开发完成。

## 1. 拟定选题

**《数字技术岗位需求与技能结构分析数仓系统的设计与实现》**

通过自主采集企业官方招聘网站的公开岗位信息，建设离线数据仓库，分析岗位类型、地区、学历、工作经验及技能要求，并通过持续采集观察样本岗位变化。企业官网为主，公共招聘平台仅作补充。

### 为什么选择这个题目

1. **有实际用途**：帮助学生确定学习与求职方向，为就业指导和课程培养提供样本依据，例如数据开发岗位需要哪些技能、不同城市与经验层级的要求有什么差异。
2. **采集与处理工作量充分**：需要多源适配、列表及详情采集、分页、日志、增量发现、快照、字段规范化、重复发布识别和技能文本提取，不依赖下载现成数据集。
3. **适合数仓建模**：岗位与地区、技能存在多对多关系；岗位发布记录和每日观察快照粒度不同，适合共享维度、分层加工和多维分析。
4. **已有真实试采依据**：腾讯、网易的第 1、2、10 页及详情已验证；本轮共取得 108 条来源岗位记录，9 个详情或简章读取成功。详见 [试采报告](../research/recruitment/README.md)。

### 业务边界

- 分析对象是所采集企业的公开招聘需求，不能宣称代表全国就业市场。
- 岗位发布记录数、去重岗位数、声明招聘人数必须区分，不计算实际录用人数。
- 薪资仅作为可选补充：腾讯、网易试采接口未披露薪资，不把缺失当零，不用其他岗位薪资推填。
- 当前更新时间不能还原历史招聘趋势；历史观察从正式快照开始积累。
- 设计稿覆盖中国大陆开发、测试、数据开发/分析、算法/AI、运维/安全等数字技术岗位；游戏美术、纯销售、纯产品及非技术项目管理、综合招聘简章不纳入核心分析。具体边界以[需求分析](design/02_需求分析.md)为准，待四人审核冻结。
- 数据来源中既有社招也有实习/校招，必须区分招聘类型。分类不清楚时保留“未知”，不凭经验猜测。

## 2. 开发顺序：先设计，再正式采集和开发

**现有可行性试采 → 前五章设计 → 冻结采集规范 → 按规范小批采集 → 联调验收与修正 → 扩大采集及持续快照 → 分层 ETL 与质量核对 → 指标与看板 → 集成验收 → 报告、PPT、录屏及答辩交付。**

**当前处于设计审核阶段：可行性试采已完成，[前五章设计稿 v0.9](design/README.md)已形成，正式采集规范尚未冻结。下一步四人审核设计及字段契约，通过后进行小批联调。下表是完整任务计划，不是全部完成记录。**

设计按老师 PPT 模板依次组织：1 项目背景、2 需求分析、3 概念设计、4 逻辑设计、5 物理设计、6 系统实现（工具和部署、数据来源、ETL、数据分层、KPI）、7 多维分析与可视化。最终报告另按 Word 模板补齐结语等内容。

概念设计使用含实体、属性、菱形联系及基数的 Chen ER 图；逻辑设计另画事实与维度关系图，不能混为一张图。分层必须体现 ODS—DWD—DWS—ADS，并明确 DIM 的作用。

设计审核至少确认：岗位范围、源记录与去重岗位的区别、快照粒度、岗位—地点及岗位—技能关系、主键、字段契约、指标分母、重复和异常处理。A/B 确认字段能采；C 确认模型可实现；D 确认指标有意义。

设计通过后先交付小批数据用于联调，再持续采集，不必等待所有数据采齐才建库。发现新来源字段改变时，以 Issue 记录并更新设计，不能随意改变交付格式。

### 2.1 从设计到交付的任务顺序

| 阶段 | 主责与配合 | 具体任务与交付物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 1. 完成前五章设计 | C 主笔，四人共同审核；D 明确业务问题，A/B 核对可采字段 | 确定地域、岗位分类、招聘类型、时间范围、实体关系、事实粒度、维度及指标；交付五章设计正文、Chen ER 图、逻辑模型、物理方案与指标字典 | 每个核心指标都有数据依据，概念/逻辑/物理设计一致；未验证指标明确列为条件性需求 |
| 2. 冻结采集规范 v1.0 | C 协调，A/B/D 会签 | 确定字段、类型、主键、缺失规则、批次与共享目录、来源映射、验收方式；填写成员与实际截止时间 | A/B 能按同一规范输出，C 能按契约读取，D 能取得分析所需字段 |
| 3. 按规范小批采集 | A 腾讯、B 网易；C/D 协助验收 | 每人主来源目标 100 个不同来源岗位，交付完整采集包；新增官网也先交可行性样本，不直接扩量 | 原始文件、JSONL、清单、日志和质量报告齐全；不是只交数据表 |
| 4. 小批联调、验收与修正 | C 主持，A/B 修采集，D 抽检技能与指标字段 | 检查格式、哈希、分页、重复、缺失、职责与要求正文；每来源至少抽检 20 条；用小批数据打通基础入仓 | 错配、解析错误和接口不一致已解决；不合格批次隔离；需要改设计时先更新规范再复验 |
| 5. 扩大采集与持续快照 | A/B 主责；C/D 同步开发 | 在批准来源、岗位及地域范围内扩量，记录覆盖率和失败页；每日保留独立批次；额外官网通过验证和字段映射后才能接入 | 每一批分别通过接入验收后进入加工，不要求等整个采集周期结束 |
| 6. 分层加工与数据质量 | C 主责，B 协助验收，A 修源问题，D 提供技能规则 | ODS 保存来源与批次；DIM 统一维度；DWD 处理类型、来源记录、岗位归并与观察快照；技能/地点关联按设计实现；交付 ETL、异常记录和层间对账 | 可从原始文件追溯到事实；重复发布和多地点、多技能连接不放大岗位数；相同批次重跑不重复入账 |
| 7. 汇总模型与 KPI 核对 | C/D 共同负责，A/B 回查原文 | 构建 DWS 汇总与 ADS 指标，计算岗位分布、学历经验、技能需求等；只有积累有效快照后才计算观察变化；交付指标 SQL、样本量与独立核对结果 | 指标定义与设计一致，未知/缺失不混入分母，至少能从图表候选结果回查原始岗位 |
| 8. 看板与业务解释 | D 主责，C 提供查询，A/B 抽检 | 建设岗位需求概览、技能结构、观察变化等看板；展示来源、日期、样本范围、筛选及下钻；写有证据的分析结论 | 看板与 ADS/独立 SQL 一致；没有足够快照时暂不展示变化结论；不把样本结论称作全国市场结论 |
| 9. 端到端集成验收 | 四人共同完成，C 组织环境复现，D 组织演示 | 从约定原始批次到 ETL、质量检查、指标、看板完整运行；验证失败处理与重跑；至少由另一位成员按 README 复现 | 关键问题关闭，复现成功，版本、数据清单和验收记录固定；不以开发者本机能运行替代验收 |
| 10. 答辩准备与最终提交 | 每人完成本人部分，D 整合展示，C 核对设计实现一致性 | 按模板整理报告和 PPT，提前录制关键操作；填写姓名学号与分工，全员彩排；答辩后完善报告，整理代码、PPT、录屏与报告 | 材料齐全，说明真实完成内容与限制；按教师通知的时间和成员姓名命名规则提交 |

### 2.2 扩大采集之后，四个人同时做什么

- **A**：维护腾讯及本人新增来源的日常采集，处理访问/解析变化、失败批次和补采，补充采集证据与操作录屏。不是交完一次数据就结束。
- **B**：维护网易及本人新增来源，同时持续检查批次、字段冲突和疑似转载；向 C 交接验收合格的批次，跟进异常原因。
- **C**：先用通过验收的小批数据开发入仓及分层 ETL，再接入后续批次，处理岗位归并、快照、共享维度和质量检查；不能直接拼接所有岗位、地点、技能记录后计数。
- **D**：在小批阶段就开展技能词典、标注样本和指标 SQL；扩量后核对提取效果、完善看板并形成业务解释。技能分析可以先做，时间变化分析必须等待足够的真实观察快照。

**采集和开发并行，但数据进入分析有先后门槛：采集批次 → 接入验收 → 分层加工 → 层间核对 → 指标发布 → 看板。** 首次全量基线应记录扫描时间和覆盖缺口；失败扫描不能据此判断岗位下架。新的观察批次不等于新增岗位，岗位变化也不等于企业实际招聘或裁员。

### 2.3 阶段结束与变更管理

每阶段用 GitHub Issue 记录负责人、交付链接、验收人和结果，通过后再移动至“完成”；时间由组内结合答辩日期安排，本说明不虚构截止日期。设计、规范或指标有变更时先记录影响，再更新文档和代码；必要时重跑受影响批次。最终演示固定一组已验收的数据批次和代码版本，持续采集可以继续，但不能无记录地覆盖答辩结果。

| 成员 | 主责 | 必须完成的开发内容 | 文档与交叉验收 |

| B：采集二与验收 | 网易及新增企业来源组二 | 网易采集器，字段映射、批次清单、质量检查，至少调研一个额外企业官网 | 数据验收及异常说明；抽检 A 的原文与提取值，A 也抽检 B |
| C：建模与 ETL | 设计整合、数据仓库 | 需求与模型组织、DDL、ODS/DIM/DWD/DWS/ADS、快照与去重规则实现、层间对账 | 前五章设计主笔、ETL/分层说明；与 D 核对指标粒度 |
| D：技能与分析 | 指标、文本提取、可视化 | 技能词典与提取规则、人工标注与效果检查、指标 SQL、看板、查询核对 | 指标口径及分析说明、展示集成；与 C 共同审核模型 |

分工不是隔离：四个人共同审核设计，每人负责本人模块的报告、PPT、操作录屏片段和代码说明。D 负责整合展示，不承担所有人的写作。工作量按可复现功能和质量证据体现，不按 commit 次数或原始记录数量机械评价。

## 4. 两位采集成员具体去哪采

### A：腾讯招聘为起点

- 官网：[腾讯招聘岗位搜索](https://careers.tencent.com/search.html)。
- 已验证列表：`GET https://careers.tencent.com/tencentcareer/api/post/Query`，参数 `keyword`、`pageIndex`、`pageSize`、`language=zh-cn`；试采每页 10 条，第 1、2、10 页成功。
- 已验证详情：`GET https://careers.tencent.com/tencentcareer/api/post/ByPostId`，参数 `postId`、`language=zh-cn`。岗位 ID 从真实列表提取，不能枚举编造 ID。
- 重点字段：`PostId`、`RecruitPostName`、`LocationName`、`CategoryName`、`Responsibility`、`Requirement`、`RequireWorkYearsName`、`LastUpdateTime`、`PostURL`。
- **必须补采岗位详情中的任职要求**，不能只交列表职责摘要。学历可能存在正文里，保留原文交由后续规则提取；源接口未提供结构化学历则填 null。
- 公司可标记来源企业“腾讯”，但不能擅自断言具体法律用工主体；派遣信息需要保留。

### B：网易招聘为起点

- 官网：[网易社会招聘](https://hr.163.com/)。
- 已验证列表：`POST https://hr.163.com/api/hr163/position/queryPage`，JSON 请求体 `{"currentPage":1,"pageSize":10}`；这是只读查询，不是投递操作。
- 已验证详情：`GET https://hr.163.com/api/hr163/position/query?id=岗位ID`。
- 重点字段：`id`、`name`、`workPlaceNameList`、`firstPostTypeName`、`reqEducationName`、`reqWorkYearsName`、`description`、`requirement`、`updateTime`、`recruitNum`、`workType`。
- 列表已返回职责和要求，若完整则无需为凑请求量重复下载每条详情；应抽查详情核对，并对截断、缺失或异常记录补采。
- 地点列表保持数组；`workType` 保留原代码，未经验证不能自行解释编码。学历字段与正文冲突时都保留并登记。

### 扩展来源如何分配

仅有两家企业会限制业务结论，建议争取更多企业覆盖。A、B 各先调研一个不同的企业官方招聘站，在 GitHub Issue 中认领，避免重复调查。新增来源名称由调研后确定，本说明不把未经验证的网站写成可采来源。

新增来源先提交可行性证据：公开入口、访问规则、真实列表、至少两页不完全相同的岗位 ID、5 条详情或完整岗位对象、字段覆盖、是否要求登录。通过后再批量采集。若不通过，提交失败原因也是调研成果，不要求绕过限制。

国家大学生就业服务平台（[公开岗位入口](https://www.ncss.cn/student/jobs/index.html)）仅作补充：已测试前两页和详情，但深分页要求登录；不得通过拆分查询等方式规避该限制。BOSS、猎聘不纳入当前主采集计划。

## 5. 两位采集成员必须交付什么

**不能只交一个 CSV 或 Excel。每个来源必须有“可运行程序＋真实数据批次＋来源与字段说明＋质量报告”。**

| 交付项 | 要求 | 放置方式 |
| --- | --- | --- |
| 采集代码 | 独立来源适配器、运行命令、配置示例、必要依赖；不把本机绝对路径写死 | GitHub `collectors/` |
| 来源说明 | 官网与接口、发现方式、访问限制、字段映射、更新方式、已知缺口 | GitHub `docs/sources/<source>.md` |
| 原始响应 | JSON/HTML 原样保存，不修改内容；文件哈希可追溯 | 共享数据目录 `raw/<source>/<batch_id>/`，不进 Git |
| 规范化数据 | UTF-8 JSONL；每行一条来源岗位观察记录；遵守下表契约 | 共享数据目录 `normalized/<source>/<batch_id>/jobs.jsonl` |
| 批次清单 | `batch_id`、来源、采集起止时间、查询范围、文件相对路径、字节数、记录数、SHA-256、解析器版本/commit | 小体积清单进入 GitHub `manifests/`；与数据批次同时交付，另含需求分析第 2.4 节规定的范围版本、查询、覆盖状态等审计字段 |
| 运行日志 | 请求次数、成功/失败、分页、状态码与业务错误、重试；去掉 Cookie、Token 等凭据 | 完整日志随批次存放，摘要进入 GitHub |
| 质量报告 | 重复、缺失、字段冲突、失败页、无法提取的记录及原因；人工抽检结果 | GitHub `reports/collection/` |
| 演示样本 | 少量不含私人联系方式的必要字段；建议仅 ID、标题、地点及来源链接，完整正文随批次交付 | GitHub `samples/`，不放整个原始数据集 |

共享数据存放位置由组内选定一个大家均可访问的网盘或共享存储，不通过聊天分散发送“最终版2”等文件。GitHub Issue 写批次路径和清单名，私有分享密码不进入仓库。数据按批次存放，不覆盖旧批次。

### 统一记录格式（v1 设计输入，设计通过后冻结）

字段名固定为英文；所有记录必须包含下列键，源未提供的可选值填 JSON `null`，不要用 0、空字符串或“无”代替。

| 字段 | 类型与要求 |
| --- | --- |
| `schema_version` | 字符串，当前约定 `1.0`；变更需讨论 |
| `source` | 字符串，例如 `tencent`、`netease` |
| `source_job_id` | 字符串；不得将长 ID 转为浮点数 |
| `batch_id` | 字符串，建议 `<source>_<UTC时间戳>`，同一来源每次运行唯一 |
| `observed_at` | 采集时间，ISO 8601，必须包含时区；统一建议使用 UTC |
| `source_url` | 岗位网页或可定位该岗位的公开接口 URL |
| `title_raw` | 原始岗位名称，必填 |
| `company_raw` | 原始企业名或可确认的来源企业名，必填；不猜法律主体 |
| `locations_raw` | 字符串数组或 null；保留多个地点，不拆成重复岗位 |
| `category_raw` | 来源岗位类别，可空 |
| `education_raw` | 来源结构化学历，可空；正文学历另由 ETL 提取 |
| `experience_raw` | 来源结构化经验，可空 |
| `description_raw` | 岗位职责或综合描述，可空 |
| `requirements_raw` | 任职要求，可空；与职责至少一项应有实质内容 |
| `employment_type_raw` | 社招/实习/校招等原始值或代码，可空，不擅自译码 |
| `salary_raw` | 原始薪资文字，可空；此阶段不补造数字薪资 |
| `headcount_raw` | 来源招聘人数的原始文本，可空；不默认 1 |
| `source_published_at_raw` | 原始发布时间，可空 |
| `source_updated_at_raw` | 原始更新时间，可空；不代替发布时间 |
| `raw_refs` | 数组，必填且非空；每项包含原始文件相对路径与 `sha256`；列表和详情均参与解析时分别列出 |
| `parser_version` | 解析器版本或代码 commit，必填 |

每批内 `(source, source_job_id)` 唯一；重复请求的原始响应可保留，但规范化文件不重复写同一岗位。跨批次同一岗位必须保留，供快照分析。字段缺失、正文冲突和解析失败另写 `quality_issues.jsonl`，注明来源 ID、规则、原因、原始文件引用；不能偷偷修正或删除。

本轮 `research/recruitment/samples.json` 是试采探索格式，**不等于本节正式 v1 契约**。正式采集器需完成字段映射后交付，避免直接把探索样本当作生产接口。

## 6. 分阶段数量、质量与验收

数量是计划目标，不是强行凑数的指标。全部记录必须真实，不能用重复转载、复制快照或模拟岗位充数。

| 阶段 | A/B 各自目标 | 通过条件 |
| --- | --- | --- |
| 设计审核 | 共同确认来源、范围、契约及指标 | 需求→字段→模型→指标能够对应；先完成前五章设计 |
| 首批联调 | 每人主来源目标 100 个不同来源岗位 ID；不足时如实说明 | 含职责/要求正文、原始响应、清单、日志与质量报告；C 能按规范读取 |
| 扩展与正式采集 | 各验证至少一个额外企业来源；按批准范围覆盖可访问页面 | 清楚记录总量与实际取得量、失败页及覆盖缺口，不把接口总数当已采数量 |
| 快照观察 | 设计首轮目标连续 14 天每天一批；实际起始日待定，不足时如实披露 | 每批独立留存；失败批次不用于判定下架；不承诺整个趋势有长期代表性 |
| 集成验收 | A/B 交接批次，C/D 对账和核对分析 | 原始与规范化记录可追踪，金额/人数/岗位数无重复计算 |

首批每来源至少人工抽检 20 条（不足则全检），覆盖不同类别、地点、缺失和冲突记录；记录抽样方法和逐项核对结果。不能只写“已检查”。人工检查发现错配岗位、伪造值或正文污染时，应修复后再交付。

通用验收条件：

- 必填标识、URL、时间和溯源引用完整；全部交付文件哈希一致。
- 列表不仅 HTTP 成功，业务响应也成功；验证翻页没有一直返回同一页。
- 每批来源 ID 无重复；两次采集重复 ID 不算新岗位。
- 缺失、无效和冲突有分列统计；岗位范围暂不确定的记录标记待分类。
- 请求失败、解析失败、过滤记录、成功记录能够解释处理去向；不将所有丢弃行混成“清洗完成”。
- 重跑不会覆盖旧证据或将相同观察重复写入当前批次；新的观察作为新批次。
- 页面或接口变化时明确报错，不导出空文件并宣称成功。

采集默认单并发、请求间隔至少 3 秒；遇网络超时可有限重试并退避，遇登录、验证码或访问限制停止并记录。网站规则更严格时以其为准。优先做稳定、可解释的采集，不使用代理轮换或绕过访问控制来凑工作量。

## 7. GitHub 管理方式

适合用 GitHub 管理代码、设计、问题、清单和验收证据；**不要把它当原始数据网盘**。本项目沿用小组已有的 `minxuanbo/data-warehouse-final-work` 仓库，当前分支内容切换为招聘选题，旧电商项目仅保留在提交历史中，组员以当前 README 为准。

建议目录（这是后续结构约定，不代表这些模块已经实现）：

```text
docs/                 设计正文、来源说明、采集契约、分工
collectors/           公共采集模块与各来源适配器
etl/                  清洗、归并、技能与快照处理
sql/                  各层 DDL、转换与指标 SQL
dashboards/           看板配置、截图与导出
tests/                有针对性的解析、质量、对账检查
manifests/            共享数据批次清单
samples/              少量必要字段样本
reports/              验收、运行摘要、分析证据
research/             可行性调研，明确与正式代码区分
data/                 本机数据，Git 忽略
```

协作规则：

1. 一个共同仓库，四个人为协作者；不要各建一套无法合并的项目。
2. 用 Issue 认领来源和模块，写清任务、交付物、验收人和组内确定的截止时间。
3. 使用 `feature/collector-tencent`、`feature/collector-netease`、`feature/warehouse`、`feature/analysis` 等分支；完成后提 PR，由另一人检查后合并。
4. 公共采集模块由 A 主维护，统一格式由 C 协调，B/D 参与审核；接口变更需在 Issue 中说明，避免各自改字段。
5. Projects 可使用“待做→进行中→待验收→完成”。PR 附运行命令、样本清单、质量结果，不只有“代码已上传”。
6. 不提交密码、Cookie、Token、个人简历、虚拟环境、数据库文件、大批原始数据与完整抓取日志；提交前检查暂存内容。
7. 小组每次阶段同步更新实际进度，计划与完成分开；每人可以说明自己的采集、设计或分析依据。

## 8. 可直接发送到群里的简版

我们拟将课程项目改为《数字技术岗位需求与技能结构分析数仓系统的设计与实现》，自己采集招聘信息，分析技能要求、地区分布、学历和经验门槛，薪资仅作有数据时的补充。腾讯、网易已做过真实试采，但这不等于正式数据已全部采集完成。

前五章设计草稿现已放在 docs/design/，先共同审核并冻结采集规范，再开展正式小批采集和联调，验收后扩大采集与数仓开发并行。A 负责腾讯来源和采集调度，B 负责网易来源及质量验收；两人各再调研一个不同的企业官方招聘来源。C 负责建模和分层 ETL，D 负责技能提取、指标和看板。每人负责本人模块的代码、报告、PPT 和演示片段。

A/B 首批各以 100 个不同来源岗位为联调目标，必须交付采集程序、原始响应、统一 JSONL 数据、来源及字段说明、文件哈希清单、日志和质量报告，不能只交 Excel。腾讯需要补采详情中的任职要求；网易列表已有完整正文时无需重复请求全部详情。薪资没有就留空，重复发布保留来源，不能凑数量。公共就业平台深分页要求登录，暂不作为主采集来源。

代码、设计、任务和验收记录放 GitHub，原始数据统一放共享目录，以批次和哈希对应。正式开始前确认姓名、截止时间及共享存储位置；之后每日快照按约定积累，数仓开发同时用已验收的小批数据推进。

完整顺序是：先完成设计、冻结规范，再小批采集和联调验收，之后才扩量。扩量期间 A/B 持续采集和验收，C 做分层 ETL，D 做技能提取与指标；随后完成 KPI 对账、看板、端到端复现和集成验收，最后按模板整理报告、PPT、录屏并全员彩排。每一步都要有交付与验收，不能采集结束后直接跳到画图。
