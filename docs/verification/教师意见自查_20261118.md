# 教师意见与现有项目自查

核查日期：2026-11-18。结论：**有真实、可保留的数仓实现，但本轮课程整改尚未闭环。不能把增加维度表、页面或测试通过等同于符合老师要求。下一步先统一分析设计，再修实现和交接材料。**

本次核对两份补充附件、第 4 章原课件、现有设计与实现，并只读查询本机 SQL Server，重跑离线测试。机器核查结果见[自查证据](../../reports/verification/教师意见自查_20261118.json)。本文件是当前问题清单，不把建议写成已完成的整改。

## 1 一致性不是增加一致性维度

这里应区分三个概念：

| 概念 | 在本项目中怎样判断 | 需要的工作 |
| --- | --- | --- |
| 图文与实现的一致性 | 图上的表、正文的键、实际 SQL 对象和看板口径是否对应 | 统一术语、对象、状态、公式和证据，不能靠新建表解决 |
| 模型与来源业务逻辑的一致性 | 一条来源岗位、一次观察、技能“优先”和“必需”等语义有没有被改变 | 明确源字段、转换规则和计数口径，逐条对账 |
| 一致性维度（conformed dimensions） | 不同分析过程是否使用相容的成员、属性含义、层次和分类口径 | 有跨过程复用需求时统一维度定义和映射；仅建独立维表并不足以证明一致性 |

第 4 章 PDF 第 26 页（页内编号 25）原文是：“数据模型总是对标源系统，始终保持数据模型与源系统中业务逻辑一致”，并说明数仓输出必须与源系统一致。这不是要求新增一个名为“一致性维度”的功能。附件中的图文一致、便于理解要求也不能这样转换。

日期、地点、技能等统一维度有合理用途，而且原有设计已经计划使用它们；昨天将部分目标落表，并非这些表本身都不该建。但它们的理由应是支持岗位需求分析及复用口径，不能作为“老师的一致性意见已经解决”的证明。也不应为了减少表数，把已有历史和映射直接删除。

| 星型模型与 ODS—DWD—DWS—ADS 的关系不清 | 已有各层职责，但主要维度图偏重对象关联与目标架构，未将一个实际分析星型、事实所在层、汇总和报表接口放在一起解释 | 部分说明正确，仍需用实际模型贯通。分层与星型是不同视角，不是选其中一个，也不因建了四个 schema 就证明分层完成 |

不能据此断言项目“只是数据库、完全不是数仓”。当前确实有分层转换、观察历史、粒度约束、技能多值关系、去重分母和分析模型。问题在于这些内容没有形成规范、易懂且与实际一致的交付。数仓也不要求事实必须有金额；岗位观察可采用无事实型观察事实，岗位日状态可采用快照，关键在于明确业务含义和可加性。

## 3 已确认的具体问题

### 3.1 设计材料仍落后于实现

- 设计目录仍称“完整一致性维度、每日归并快照、正式发布和调度恢复仍未完成”。第 6、7 章仍称只有四页报表，KPI 展示和层次分析未完成。实际工程已有七页，SQL 中已有样本快照和发布对象。
- 逻辑设计将日事实主键写成 `(build_id,date_key,job_key)`；`sql/004_release_schema.sql` 实际使用 `(release_id,date_key,job_key)`，其中 `build_id` 是单来源技能分析输入，不是整组日快照的发布版本。
- 物理设计仍写 `dim.date` 和单行 `singleton` 发布指针；实际是 `dim.calendar_date` 和按 `sample/formal` 通道区分的指针。未知维成员固定为 0 也只是原设计约定，新增维表并未据此统一初始化。
- 目标图中的 `fact_collection_run` 尚无对应实际表；当前运行信息主要在 `audit.collection_batch`。不能把计划对象展示为实际完成的业务事实。

这些差异直接对应老师“保持一致性”的意见。原文区分目标和实际虽有帮助，但目标、历史状态、当前状态交错出现，读者仍会得到互相矛盾的答案。

### 3.2 岗位分类存在两套语义

需求 §2.1 规定“按职责优先于名称分类”，新增 `warehouse/normalization.py` 却按标题正则优先，再参考源类别。旧 Power BI 的 `Jobs.category_group` 实际来自官网原类别，新 `SnapshotJobs.category_group` 来自统一分类，名称相同但含义不同。

例如网易 71196 的源类别为“人工智能”，新类别为“算法/AI”。这种映射本身可以合理，但必须明确哪个字段叫“来源类别”、哪个叫“标准岗位类别”，分类优先级经设计确认并抽检。相关 DAX 期望值生成也调用同一个 `classify` 函数，因此它能验证管线计数，却不能独立证明分类业务规则正确。

招聘类型维表也不能视为已完成社招/校招/实习分析：当前发布 4 中，网易 100 条、腾讯 99 条仍为“来源代码未释义”，腾讯另 1 条为“未知”。保留未知是正确处理，但需将对应分析能力标为受限，核实代码映射后才能使用。

### 3.3 当前 Power BI 有不安全的自动关系

当前 `model.bim` 包含：

`SnapshotJobs[content_json] ↔ Jobs[content_json]`

该关系为双向、以正文 JSON 作为一侧唯一键。正文是内容，不是岗位或快照身份。一个岗位连续两天正文不变时，快照中会重复出现同一正文，不能继续保证此关系的一侧唯一性；也可能把旧页筛选意外传给新页。应按照经审核的岗位身份、日期、构建及共享维度关系组织筛选，去除这种正文连接，并检验其他自动关系。

这不是现在所有指标都已算错的结论，而是已确认的模型设计缺陷及扩量风险。昨天 81 项 DAX 记录绑定的模型哈希为 `e814292a…`，当前文件为 `ed5304af…`，不能用旧结果为当前文件直接背书；改正关系后需要重新验收当前模型和交互。

### 3.4 新增实现还不能让接手者顺利理解

当前有 30 个 dbt 模型，但新增的 10 个 `release_*` 模型没有对应 YAML 模型说明；旧材料“20 模型、237 列均已说明”不覆盖新内容。`warehouse/README.md` 没有给出新流水线的完整使用说明，`warehouse/pipeline.json` 的固定输入又引用被 Git 忽略的 `.local` 批次、技能结果和词典路径。

这些输入可通过旧准备脚本恢复，并不意味着绝对不能复现；问题是接手者需要先从历史说明和多个脚本中推断前置步骤。应有一个从干净克隆到固定样本成功的当前入口，说明依赖、准备命令、配置、预期结果、日志及失败处理。独立复现通过后，才算回答了老师“让人看得懂”的维护要求。

### 3.5 调度与质量指标不能替代业务分析

`scripts/run_pipeline.py` 加工已经验收的批次，不调用采集器，也不自动从 GitHub 拉取组员新批次。计划任务即使成功运行，也不代表新一天已真实采集。本次没有重新验收计划任务的注册及运行状态。

三项质量 KPI 可以作为系统质量证明，应保留；但它们不是岗位需求主题的分析结论。“批准范围遍历完成率 0%”反映当前 partial 样本，不应为了绿灯改成 complete。需要另外交付岗位结构、技能需求和门槛差异的真实分析，并对每个结论交代样本、观察日、分母和限制。

## 5 先设计再整改的明确顺序

### 第一步 收敛主题与决策问题

主主题建议明确为“公开数字技术岗位需求”，技能需求、岗位门槛和地区结构是它的分析方向。腾讯、网易是来源，不是两个主题；采集/数据质量是支撑主题。

先形成下表并与需求第 2 章统一，而不是先扩表：

| 分析方向 | 使用者及决策 | 所需分析 | 数据条件 |
| --- | --- | --- | --- |
| 技能需求 | 就业指导或培训规划人员选择训练重点 | 按标准岗位类别、地点比较技能及组合覆盖 | 固定正文集合；计不同岗位，不计证据频次 |
| 岗位门槛 | 指导人员比较学生适配的岗位方向 | 学历/经验分布及与技能的交叉分析 | 未知、冲突、不限分开；披露可用覆盖 |
| 地区与类别结构 | 人才服务或培训组织选择关注地区和岗位方向 | 同一批准范围的城市、类别分布 | 多城市去重；企业样本不代表全市场 |
| 观察变化 | 同一使用者调整后续观察重点 | 同范围相邻完整日的集合变化 | 连续真实批次；条件不足时不计算 |

上述使用场景是设计建议，不能写成已经访谈过真实企业。作业要求强调决策分析，应明确一个组织使用方和具体动作，避免只写“方便查询、支持分析”。

### 第二步 重整概念与逻辑设计

1. 第 3 章以“主题、业务问题、维度/层次、度量”的信息包为主；两张业务 Chen ER 移到辅助说明，不再作为数仓概念设计主成果。
2. 按“业务过程→粒度→维度→事实”形成一张设计决策表。当前快照如沿用一对一来源身份，其一行应称“固定发布版本内，某分析日的一条来源岗位状态”，不要称已完成跨源归并。
3. 画一张与实际 DDL 对应的岗位快照扩展星型图，在事实表名下直接写粒度，标出维度键、计数标记与技能/地点桥，参照第 4 章 PDF 第 25、56 页的表达。
4. 源岗位观察作为底层观察过程，采集运行和发布作为技术审计；只有明确跨业务过程复用需求时，再用总线矩阵解释整体星座，不能为了叫“星座”凑事实表。
5. 一次决定分类优先级、岗位身份、两个版本键、未知处理和时间语义，再落实到代码。当前样本星型、后续连续日和未来跨源归并分别标注状态。

### 第三步 用同一模型解释分层

| 视角/层 | 应讲清的内容 | 本项目示例 |
| --- | --- | --- |
| 星型/扩展星型 | 一个分析过程怎样由事实、维度和桥表组成 | `dwd.fact_job_daily` 关联日期、来源、企业、类别等维度，技能和城市经桥表 |
| ODS | 怎样保存可追溯的原始输入 | `ods.posting_record`、`ods.raw_response` |
| DWD 与 DIM | 怎样整理细粒度分析事实、历史和统一描述 | 观察、版本、日状态、技能/地点桥及对应维度 |
| DWS | 怎样按主题复用计数、分母与汇总 | `dws.release_daily_summary`；其他主题汇总按需求设计，不能虚写已经全部建好 |
| ADS | 怎样为具体指标、明细和页面提供口径固定的接口 | `ads.release_job_detail`、`ads.release_skill_demand` 等 |

星型说明“怎样关联和分析”，分层说明“怎样加工和组织职责”。维度不等于某一个串行处理阶段；DWS/ADS 也不要求再各复制一套同样的星型。课件的 NDS/DDS 是其案例架构，不能机械地与本项目 ODS/DWD/DWS/ADS 一一等号对应。

### 第四步 修实现并以当前成果验收

先改 Power BI 正文双向关系与不必要自动关系；再按审核后的分类和口径重建，必要时生成新版本而不覆写旧证据。统一新旧页面的字段含义，业务页名称建议改为“岗位需求多维分析”，不以建模技术名“一致性维度分析”代替业务主题。

验收需同时覆盖：DDL 粒度与唯一性、独立人工分类/技能核对、分母和多值去重、同一岗位多日正文不变、固定版本导入，以及页面筛选/钻取。现有程序测试保留，补其未覆盖的业务和多日情形；100 岗复核包目前仍 pending，不能将生成复核包算作人工验收完成。

### 第五步 整理唯一交接入口

统一更新 README、七章正文、图与对象字典；补新模型说明、字段级来源映射和当前复现命令。历史报告保留日期，但不再作为当前操作入口。交由另一成员按干净环境说明复现并核对结果，再组织期末报告、PPT 与录屏。
