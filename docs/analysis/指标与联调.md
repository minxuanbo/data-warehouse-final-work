# 首版指标口径与 C/D 联调

## 当前集合与限制

固定 `source=tencent`、`batch_id=tencent_20261031T093102Z_366ad0a4`。P 是本批 100 个不同来源岗位，键为 `(source,source_job_id,batch_id)`。本轮没有跨源归并或正式每日快照，因此不用“独立招聘机会数”名称，不跨批加总。

T 是 P 中职责或要求至少一个字段含非空文本的岗位，当前为 100。它是“有可解析正文”的机械判定，不等于每条正文已经业务验收、技能已经完整收录。结构化维度缺失单独归“未知”；空分母返回 null，页面显示“—”。

| 指标 | 分子/值 | 分母 | 未知与筛选 |
| --- | --- | --- | --- |
| 来源岗位数 | P 中不同身份数 | 无 | 仅本批，筛选后重算 |
| 正文覆盖率 | T 数量 | P 数量 | 无正文不删除，另报覆盖缺口 |
| 源类别分布 | 各 `category_raw` 组不同岗位数 | P 数量 | 当前技术99、未知1；这不等于已完成开发/测试/数据/算法/运维安全主类别规范化 |
| 城市分布 | 地点数组包含该城市的不同岗位数 | 当前 P 数量（需占比时） | 原地点未知单组；不根据标题扩展城市；多地点各计1，跨城市可重叠 |
| 学历分布 | 各 `education_raw` 组不同岗位数 | P 数量 | 当前100条结构化未知；正文有学历也不在此冒充已标准化；以后由C/D审核映射 |
| 经验分布 | 各 `experience_raw` 组不同岗位数 | P 数量 | “不限”与未知分开；来源值与正文有差异时先留原值和冲突 |
| 技能出现占比 | T 中该技能有 `eligible_for_metric=true` 证据的不同岗位数 | T 数量 | 含必需、优先、明确提及，排除否定/不确定；未匹配任何词典技能的有效正文仍在分母 |
| 按强度技能占比 | T 中该技能在指定强度有有效证据的不同岗位数 | T 数量 | 同岗可同时有职责提及与要求优先，各强度结果不可相加当独立岗数 |
| 技能组合岗位数/占比 | T 中同时含两项有效技能的不同岗位数 | T 数量（占比） | 每岗每技能先去重，再生成无序技能对；不算证据条数或无意义自配对 |
| 招聘类型 | 当前只列原始代码分布 | P 数量 | 未经来源验证不将40001001等代码擅自翻译为社招/校招 |

城市、源类别、经验是样本筛选；技能分母从筛选后的 T 重新计算。看板技能下钻只改变明细列表，不改变分母。没有匹配技能不等于“岗位不需要技能”；词典范围较窄、备选组保守排除都会降低出现占比，当前数字只用于联调。

不做薪资图、趋势图、岗位新增/下架图或企业招聘增长结论。没有薪资不能填0；没有完整连续快照不能用当前更新时间还原历史。

## 看板草图

`reports/analysis/<batch_id>/dashboard.html` 可离线打开，无外部 CDN 或库。上方持续展示批次、单来源与partial提示；筛选原始城市/类别/经验。第一行是来源岗位数、正文覆盖、有有效技能证据岗位数、结构化学历未知数。第二行是技能前12、城市及经验分布；第三行是技能对前8及质量/验证边界。下方岗位表点ID可见技能、强度、语境、原文、字段、位置与版本。

正式 Power BI 页面沿用同一粒度与未知策略。等 C 的只读接口和技能桥就绪后，再核对筛选传播、版本键、每个图的分母及岗位下钻，不用当前 HTML 冒充 Power BI 交付。

## 已核对的 C 接口与交接方式

读取了 `origin/feature/warehouse` 的三个 ADS 试验视图定义，没有把它们合并到本分支。当前 main 没有这些视图。

| C 接口 | 已见粒度/字段 | D 使用方式 |
| --- | --- | --- |
| `ads.trial_overview` | 试验批次概览 | 用批次过滤后与离线100岗及正文覆盖核对 |
| `ads.trial_city` | 试验城市分布与状态 | 原地点分布对账，不能替代行政区划裁定 |
| `ads.trial_job_detail` | 来源岗位×批次；source/id/batch/version_key/content_json/source_revision/状态 | 先固定批次；由Python JSON或OPENJSON解析长正文，不用SQL JSON_VALUE截取长正文 |

接口定义里 `dataset_status` 仍写“试验数据：未正式验收”；本批 main 的采集清单已技术accepted，两者不是同一层级的验收。C/D联调需确认C入库是否已使用新版清单与revision，不由D自行更改仓内状态。

交给 C：`skill_evidence.jsonl` + `dictionary.json` + `input_provenance.json`。C 按 `(source,source_job_id,batch_id)` 在已选输入版本中查唯一 `version_key`，核对 jobs 文件哈希与正文哈希，再映射 dim_skill / bridge_version_skill。不能从 `version_key` 数值或标题猜对应关系；也不能把D的正文哈希当作C的SCD2内容哈希。

同一技能桥项可以保存多段证据。桥项至少包含内容版本、标准技能、提取版本、要求强度；证据保留原字段/片段/位置/语境。C 负责入库、层间建模、事务和正式发布，D 不直接建或更新正式仓表。

## SQL候选与验收清单

`sql/analysis_trial_checks.sql` 只读 C 的试验岗位接口，技能 JSON 数组作为参数输入/表变量解析，不创建表。SQL中的候选桥、岗位去重和分母与离线定义对应；代码已静态核对视图字段，**没有真实数据库执行证据**。执行前C必须确认该批试验数据已入库、接口存在、只读身份可用。

C/D双方核对：岗位100、正文100、城市60/19/15/3/3；技能与组合先去重；未匹配正文仍在分母；强度/否定/备选过滤一致；比率为“本次分子/本次分母”，不平均各组比率。9条城市冲突、2项范围疑问和经验差异先留痕，不能静默修改原文后宣称对账通过。

## 本轮新增的字段范围问题

28岗原始详情的 `ImportantItem` 有补充要求，当前统一 `requirements_raw` 仅映射 `Requirement`，与采集器说明一致。现有技能占比不覆盖附加段落；不能据主字段一一对应就宣布全部详情正文已覆盖。清单见 `reports/analysis/<batch_id>/supplemental_requirements.csv`，需C/采集同学共同确认是否增加附加要求字段或带来源标记合并，并升映射/批次版本。

本轮验证候选分数与强度差错见[验证说明](验证说明.md)；3条经验口径差异和额外工作地信息见 `data_issues.csv`。确认前保留源值，本轮按当前字段口径继续文件联调。
